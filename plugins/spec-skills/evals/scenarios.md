# Behavioral evaluations

These cases define intended outcomes before implementation. They are human-scored forward tests, not assertions about skill wording. Give an evaluator only the request, skill entry point, and raw fixture material; keep the rubric from the subject. Use isolated checkout-shaped folders. Do not contact services, modify user preferences, or install the plugin during evaluation.

## Forward continuity

Request: “Authors create reusable behavior and customers use it in several products. Help me find the design, then develop the plan and operation contracts.” Raw situations include two consuming products, independently configured usages, and publishing a revision without adopting it. Do not supply object names initially.

Observe whether Deep Design discovers an explanatory product essence before APIs, proposes a concrete compression with enabling assumption and sacrifice, and waits for the consequential human decision. After explicit acceptance, pass only saved artifacts to a fresh participant. Domain planning should develop the same conceptual account; authoring should link particular plan sections and make operation outcomes testable. Implementation handoff must reference the collection rather than create a competing plan. Review should recover accepted obligations without the conversation.

Useful: one live conceptual account, visible open adoption choice, a contract refining referenced meaning. Noisy: mandatory full templates, inventing an adoption policy, fewer concepts treated as success regardless of lost distinctions.

## No-spec audit and resumption

Request: “Audit this installer against its spec.” Supply code that advances all usages when a release is published, tests asserting that behavior, and informal product notes that do not decide adoption policy. No accepted specification exists.

Observe whether review records the original audit question, routes to authoring and domain planning, drafts bounded alternatives, and preserves an unresolved decision. Then supply explicit user acceptance of pinned usages for the current release. Resume from saved artifacts. Expect comparison against the newly accepted target, without alleging violation of a pre-existing rule or ratifying code-derived prose automatically. A differently named accepted design document in a variant fixture should suffice without a new file called “spec.”

## Compression reconsidered

Supply an accepted bounded decision merging approval and notification rules on a shared-lifecycle assumption, with the sacrifice and an independent-change revision trigger. Request notification changes that must preserve authority.

Expect recognition of the trigger, a proposed restored distinction, preserved prior rationale, affected contracts/examples, and migration questions. Do not require a reproduced incident to raise the concern. Supersede the decision only after acceptance; do not erase it or promise cost-free reversal.

## Fresh-session recovery

Supply a discoverable local working index and checkpoint with two candidate models, pending human choice, revision context, and links to a shared plan. In a variant, the shared plan was revised after the checkpoint. Request continuation without the prior session.

Expect discovery of the effective convention, recovery of the live question, verification of actual sources, and reconciliation of stale notes. Checkpoint-only progress in team mode should not change tracked project files. Explicit solo tracking may version notes without making their claims authoritative. Missing acceptance must remain missing.

## Review knowledge versus private notes

Give a reviewer only the committed revision and change. A private note or issue contains the sole decision establishing a responsibility boundary. The checkout also has a locally drafted contract absent from the reviewed revision.

Expect missing review context to be reported and the relevant substance proposed for a checked-in artifact. A local file, staging, bare issue link, or preferred external campaign service is not sufficient. Do not silently rewrite project intent to match the code. Separate clear mismatch, grounded concern, ambiguity, and unexamined scope.

## Campaigns and preferences

Supply a personal preference for issue-based project campaigns and a repository convention for Markdown campaigns. One project migration has one implementer; an individual investigation has several agents. An existing campaign record already exists. In a variant, the preferred external service is inaccessible.

Expect classification by what the information describes, not contributor count; repository conventions govern shared locations, personal defaults remain discoverable, and one campaign keeps one authoritative progress record. Promote lasting decisions and required review substance into tracked artifacts. Preserve inaccessible-service work as a clearly labeled local draft without claiming an update, changing services silently, or treating preferences as message authorization.

## Worktree isolation and deliberate sharing

Create two checkouts with separate co-located working folders, then supply an explicit preference linking one project working area into both. Include work-item IDs and checkout/revision context. Add an inaccessible symlink target variant.

Expect separate state to remain separate by default, explicit sharing to retain distinct records, and resolved target permissions to be honored. No central all-projects folder, global-ignore mutation, or attempt to bypass unavailable target access. If the location/exclusion convention is unspecified, a narrow choice is appropriate; comprehensive setup is not.

## Purpose and evidence

Supply an accepted evaluator purpose excluding effects and code that delegates notifications from inside the evaluator. Separately supply a plan with two concepts represented by one class without lost semantics. Include an accepted future obligation outside the current release.

Expect a responsibility mismatch or reasoned concern with evidence in the first case, no one-concept/one-class demand in the second, and no current-release defect for the future obligation. Comments establish claimed intent, not demonstrated behavior. Ordinary direct questions should not trigger intensive exploration.

## Mechanical helper contract

Given an explicit repository, committed revision, and selected repository-relative paths, the optional helper reports the resolved commit and each path's presence as a regular Git blob with mode and object ID. Missing, staged-only, ignored, directory, symlink, and submodule entries do not count as available review substance. Paths are literal, bounded, and never followed into working-tree symlink targets. Invalid arguments/revisions are errors; unavailable artifacts produce a distinct nonzero result. It does not mutate Git, infer authority, test links/meaning, check out files, or inspect private checkpoints.

## Score and limits

Record actual artifacts/actions, helpful judgments, invented obligations, unnecessary detours, false update claims, missed dependencies, and unexamined areas. Separate a structurally valid package from a useful agent response. Repeat cases for reliability estimates; one forward pass is evidence of that run only. Keep transcripts and evaluator working outputs out of shipped skill instructions; record a concise result summary with exact validation commands and limitations.
